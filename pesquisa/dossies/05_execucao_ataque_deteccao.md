# EternalBlue (MS17-010): execução do ataque ponta a ponta e detecção (descrição conceitual/defensiva)

Escopo: descrição conceitual, em nível de livro-texto e documentação pública, para disciplina universitária de segurança. Não há código de exploit, shellcode nem bytes de payload nestas notas. Data de referência: novembro/2026. A maior parte das fontes primárias é de 2017–2020 (o exploit é de 2017); a documentação Microsoft Learn citada foi atualizada em 2026.

Convenções: "[verificado]" = li a página citada nesta sessão. "[snippet]" = apenas resultado de busca, não li a página inteira. "[secundário]" = blog/wiki de terceiros.

## 1. Fases do ataque (kill chain): reconhecimento, exploração, implante DoublePulsar, entrega de payload, pós-exploração e comportamento de worm

### Takeaway
A cadeia típica é: varredura da porta TCP 445 e checagem de MS17-010 (Nmap/Metasploit scanner) → sequência de pacotes SMBv1 malformados com grooming de pool de kernel e overflow em srv.sys → shellcode de kernel (DoublePulsar no caso do WannaCry e do FuzzBunch) → injeção de código em modo usuário (DLL/ransomware/Meterpreter) → persistência/propagação worm (varredura da sub-rede e da Internet na 445). O mecanismo de bug está bem documentado pela Check Point; o detalhe de qual processo é alvo da injeção é a parte com fontes conflitantes.

### Cited Findings

**Fase 0: contexto e vulnerabilidade**
- EternalBlue faz parte do vazamento "Lost in Translation" do grupo Shadow Brokers (abril/2017), explora o driver SMBv1 do servidor e foi corrigido em MS17-010 (CVE-2017-0144 no artigo da Check Point; a Microsoft cita CVE-2017-0145 para o exploit usado pelo WannaCrypt; o módulo Metasploit lista CVE-2017-0143 a 0148 como família). Há divergência de numeração de CVE entre fontes. — [Check Point Research](https://research.checkpoint.com/2017/eternalblue-everything-know/); [Microsoft Security Blog – WannaCrypt](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/); [Rapid7 DB – ms17_010_eternalblue](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/) [verificados]
- Patch MS17-010 foi lançado em 14/03/2017; o vazamento ocorreu em 14/04/2017. — [Nmap NSE smb-vuln-ms17-010 (disclosure date 2017-03-14)](https://nmap.org/nsedoc/scripts/smb-vuln-ms17-010.html); [CISA TA17-132A](https://www.cisa.gov/news-events/alerts/2017/05/12/indicators-associated-wannacry-ransomware) [verificados]; data do vazamento (14/04/2017) via [Wikipedia – EternalBlue (espelho)](https://ipfs.ssi.eecc.de/ipns/en.wikipedia-on-ipfs.org/wiki/EternalBlue) [secundário/snippet]
- Versões afetadas pelo exploit: a Check Point afirma que "EternalBlue works on all Windows versions prior to Windows 8" (a técnica dependia de região de heap HAL executável antes de Win8/Server 2012). O módulo Metasploit lista apenas arquitetura x64. A Microsoft afirmou que o WannaCrypt atingia Windows 7/Server 2008 e anteriores e que Windows 10 não foi alvo do ataque. — [Check Point](https://research.checkpoint.com/2017/eternalblue-everything-know/); [Rapid7 DB](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/); [Microsoft](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/) [verificados]

**Fase 1: reconhecimento e varredura (porta 445)**
- `smb-vuln-ms17-010` (Nmap NSE, categorias vuln e safe, autor Paulino Calderon): conecta à árvore IPC$, executa uma transação no FID 0; o status "STATUS_INSUFF_SERVER_RESOURCES" indica provável host sem patch; também verifica códigos de erro conhecidos de sistemas corrigidos. Uso documentado: `nmap -p445 --script smb-vuln-ms17-010 <alvo>`. — [Nmap NSE doc](https://nmap.org/nsedoc/scripts/smb-vuln-ms17-010.html) [verificado]
- `auxiliary/scanner/smb/smb_ms17_010` (autores Sean Dillon e Luke Jennings): usa a mesma ideia (IPC$ anônimo + transação em FID 0; status de "insufficient server resources" = sem patch) e, se o host aparenta estar sem patch, também verifica infecção prévia por DoublePulsar (shellcode ring 0). Não exige credenciais em configurações padrão de servidor. — [Rapid7 DB – smb_ms17_010](https://www.rapid7.com/db/modules/auxiliary/scanner/smb/smb_ms17_010/) [verificado]
- `smb-double-pulsar-backdoor` (Nmap NSE, categorias vuln, safe, malware; baseado no script Python de Luke Jennings/Countercept): verifica se o alvo roda o backdoor DoublePulsar. — [Nmap NSE doc](https://nmap.org/nsedoc/scripts/smb-double-pulsar-backdoor.html) [verificado]
- Para varrer redes inteiras, o README do Countercept sugere masscan para achar hosts com 445 (SMB) ou 3389 (RDP) abertos e depois rodar os scripts de detecção. — [Countercept/WithSecure doublepulsar-detection-script](https://github.com/countercept/doublepulsar-detection-script) [verificado]

**Fase 2: exploração (conceitual)** — todos os itens abaixo: [Check Point Research – EternalBlue Everything There Is To Know](https://research.checkpoint.com/2017/eternalblue-everything-know/) [verificado], salvo indicação.
- Componente vulnerável: driver SMBv1 do servidor (srv.sys); o grooming usa estruturas do driver SMBv2 (srvnet.sys), cujas alocações ficam adjacentes no pool de kernel.
- Três bugs encadeados: (A) erro de cast ao converter lista de atributos estendidos (FEA) do formato OS/2 para NT, em que o tamanho é atualizado só nos 2 bytes inferiores de um campo de 4 bytes, gerando overflow de buffer em non-paged pool ("Instead of shrinking the SizeOfListInBytes, the function enlarges it"); (B) erro de parsing: sub-comandos de transação com larguras de dado diferentes (16 bits em Trans2, 32 bits em NT Transact), sem verificar qual transação iniciou a sequência, permitindo que um pacote secundário seja interpretado com a largura errada e dispare o bug A; (C) alocação de pool controlada pelo atacante via Session Setup em formato "extended security" sem a flag correspondente, interpretado como NT security, que desalinha o byte count e aloca um chunk de tamanho escolhido.
- Grooming de pool (conceitual): abrir várias conexões SMBv2 para espalhar estruturas srvnet; usar o bug C para alocar e liberar um espaço de tamanho adequado; iniciar transação SMBv1 fragmentada cujo buffer convertido cai nesse espaço, segurando o último pacote secundário até o layout estar pronto; ao completar a transferência o overflow sobrescreve ponteiros no cabeçalho da estrutura srvnet vizinha (ponteiro de MDL e ponteiro da estrutura de handler da conexão).
- Execução: com o MDL redirecionado, os dados seguintes são gravados em endereço fixo no heap do HAL (executável antes do Windows 8/Server 2012; endereço estático até o Windows 10 e diferente em x86/x64); o atacante coloca ali uma estrutura de handler falsa seguida do shellcode (o artigo identifica o shellcode como DoublePulsar); quando as conexões srvnet corrompidas são fechadas, o servidor chama o ponteiro de handler e o fluxo cai no shellcode, resultando em execução de código em kernel.
- Observações de rede do artigo: sessão nula em IPC$ era permitida por padrão em sistemas anteriores ao Windows 8; o tráfego mostra transações SMBv1 com pacotes secundários misturados a múltiplas conexões SMBv2 e um pacote final retido; a exploração "usually takes more than a single attempt", logo tentativas repetidas de uma mesma origem são um sinal plausível. O artigo não publica assinaturas de detecção.
- Descrição equivalente na documentação do Metasploit: overflow em `Srv!SrvOs2FeaToNt` (tamanho calculado erroneamente em `Srv!SrvOs2FeaListSizeToNt`), pool groomed para sobrescrever um buffer SMBv1 e sequestro de fluxo concluído em `srvnet!SrvNetWskReceiveComplete`. — [Rapid7 DB – ms17_010_eternalblue](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/) [verificado]
- Confiabilidade: Metasploit classifica o módulo como "Average", orienta rodá-lo repetidamente, descreve sucesso "em sequências" com períodos de resfriamento e avisa que pode causar BSOD/reboot. O SANS ISC observou que o exploit tenta 3 vezes por padrão e que, após tentativas repetidas, o Windows 7 de teste travou. — [Rapid7 DB](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/); [SANS ISC diary 22304](https://isc.sans.edu/diary/22304) [verificados]
- Variante "ms17_010_psexec" (família EternalRomance/EternalChampion/EternalSynergy; CVE-2017-0143, 0146, 0147): usa confusão de tipo entre requisições Transaction e WriteAndX mais uma condição de corrida em Transaction para obter write-what-where, sobrescreve informação de sessão da conexão com uma sessão de Administrador e então roda o payload padrão do psexec. A página diz ser "more reliable than the EternalBlue exploit, but requires a named pipe"; plataforma Windows x86 e x64; ranking Normal. — [Rapid7 DB – ms17_010_psexec](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_psexec/) [verificado]

**Fase 3: implante DoublePulsar (conceitual) e como é detectado/"pingado"**
- Papel: DoublePulsar é o payload primário dos exploits SMB e RDP no FuzzBunch; é um backdoor de kernel cujo trabalho é carregar código secundário, não abre portas nem spawn de shell. Resolve ntoskrnl por tabela de interrupções, localiza srv.sys e sobrescreve uma entrada da tabela de despacho Trans2 do SMB (array de ponteiros de função na seção de dados de srv.sys) por um hook que repassa requisições normais ao handler original. — [zerosum0x0 – DoublePulsar Initial SMB Backdoor Ring 0 Shellcode Analysis](https://zerosum0x0.blogspot.com/2017/04/doublepulsar-initial-smb-backdoor-ring.html) [verificado]
- Protocolo de controle: o ping é uma requisição Trans2 que usa o subcomando reservado e não implementado SESSION_SETUP (0x000e), sem relação com o SMB Echo. Campos de timeout, multiplex ID, signature e parâmetros de session setup carregam significado próprio. O opcode (ping, exec, kill) é codificado no campo timeout (o artigo Forcepoint descreve o opcode como soma dos bytes do timeout, mascarada para um byte). — [Forcepoint X-Labs, parte 2](https://www.forcepoint.com/blog/x-labs/evasions-used-shadow-brokers-tools-danderspritz-and-doublepulsar-part-2-2) [verificado]; valores 0x23 (ping), 0xc8 (exec), 0x77 (kill) vieram apenas do resumo de busca da mesma página [snippet]
- Indicador de rede mais citado: em condições normais a resposta repete o Multiplex ID da requisição; o ping de DoublePulsar usa MID 65 (0x41) e a resposta de host infectado vem com MID 81 (0x51), enquanto um host limpo devolve STATUS_NOT_IMPLEMENTED com MID 65. — [SANS ISC – Detecting SMB Covert Channel (Double Pulsar)](https://isc.sans.edu/diary/22312) [verificado]
- Códigos de status via MID: Forcepoint descreve diferença de 0x10 como sucesso, 0x20 parâmetros inválidos, 0x30 falha de alocação [snippet de busca; a fetch não repetiu os valores numéricos]; o pacote Zeek EternalSafety alerta quando o servidor muda o MID para a faixa 81 a 83 no meio de uma transação. — [Forcepoint](https://www.forcepoint.com/blog/x-labs/evasions-used-shadow-brokers-tools-danderspritz-and-doublepulsar-part-2-2); [zeek-EternalSafety](https://github.com/0xl3x1/zeek-EternalSafety) [verificado]. Observação: a hipótese do enunciado de MIDs "0x41/0x42/0x43" não aparece nas fontes; o que aparece é 0x41 (requisição/host limpo) e 0x51 (infectado), com 0x52/0x53 inferidos da faixa 81–83 do Zeek e da regra Snort 5000072 que cita MID 82 [secundário: [Hackers-Arise](https://www.hackers-arise.com/amp/2018/11/30/network-forensics-part-2-packet-level-analysis-of-the-eternalblue-exploit) via snippet].
- A resposta ao ping carrega, no campo signature, a chave XOR usada depois para ofuscar o payload e indica arquitetura x86/x64; o upload é fragmentado em vários pacotes com XOR rudimentar. — [Forcepoint](https://www.forcepoint.com/blog/x-labs/evasions-used-shadow-brokers-tools-danderspritz-and-doublepulsar-part-2-2); [zerosum0x0](https://zerosum0x0.blogspot.com/2017/04/doublepulsar-initial-smb-backdoor-ring.html) [verificados]
- O implante aceita o ping sem autenticação; por isso o script do Countercept reimplementa o ping para saber se o host está infectado e possui flag `--uninstall` que tenta remover o implante remotamente usando o mecanismo de opcodes (kill). O README avisa que alguns Windows não testados podem responder com erro (ex.: Server 2012 rejeita a sequência). — [Countercept/WithSecure README](https://github.com/countercept/doublepulsar-detection-script) [verificado]
- Manutenção do implante: o autor do zerosum0x0 afirma que a remoção não pode ser verificada e que a máquina comprometida deve ser reconstruída, não confiada após a limpeza. — [zerosum0x0](https://zerosum0x0.blogspot.com/2017/04/doublepulsar-initial-smb-backdoor-ring.html) [verificado]
- Evasões do framework: respostas válidas disfarçadas de erros, nenhuma porta nova de escuta, criptografia rudimentar; no DanderSpritz/PeddleCheap: pacotes TCP sobrepostos, rotação de portas, port knocking e dados binários rotulados como imagem em HTTP. — [Forcepoint](https://www.forcepoint.com/blog/x-labs/evasions-used-shadow-brokers-tools-danderspritz-and-doublepulsar-part-2-2) [verificado]

**Fase 4: entrega de payload (kernel → modo usuário)**
- Payload via DoublePulsar: o comando exec envia o shellcode em partes, decifra com chave derivada da signature da sessão e executa a partir de memória executável recém-alocada; a cadeia de injeção de DLL é descrita no zerosum0x0, com comentário do autor dizendo que o alvo padrão é o lsass.exe (SYSTEM). O mesmo post não descreve injeção baseada em APC (cita APC apenas como sugestão para um port Metasploit). — [zerosum0x0](https://zerosum0x0.blogspot.com/2017/04/doublepulsar-initial-smb-backdoor-ring.html) [verificado]
- Análise da F-Secure (resultado de busca): o payload de kernel enfileira uma APC em uma thread do processo alvo e a carga da DLL ocorre em shellcode de modo usuário executado pela APC; no teste descrito o alvo foi calc.exe e o payload de kernel apaga seu próprio código e a DLL após a APC; o loader de modo usuário é um reflective loader genérico. — [F-Secure – kernel DLL injection](https://blog.f-secure.com/analyzing-the-doublepulsar-kernel-dll-injection-technique) e [F-Secure – usermode analysis](https://blog.f-secure.com/doublepulsar-usermode-analysis-generic-reflective-dll-loader) [snippets; as páginas redirecionam e não consegui lê-las]
- Conflito explícito: lsass.exe como alvo padrão (comentário do autor no zerosum0x0; resumo genérico em [securityscientist.net](https://www.securityscientist.net/blog/12-questions-and-answers-about-doublepulsar/) [secundário, baixa confiança]) versus calc.exe em um teste da F-Secure (provavelmente processo escolhido para o experimento). Tratar "APC injection em lsass.exe" como afirmação a ser qualificada no relatório.
- WannaCry: após explorar, o malware executa shellcode de kernel que parece adaptado do DOUBLEPULSAR público, e solta/executa o dropper do ransomware em x86 e x64 (a Microsoft não menciona lsass nem injeção). A Talos afirma que o WannaCry usa ETERNALBLUE para acesso inicial, implanta DOUBLEPULSAR e o usa para rodar o ransomware; se DOUBLEPULSAR já estiver presente, o malware o usa diretamente. — [Microsoft](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/); [Cisco Talos – WannaCry](https://blog.talosintelligence.com/wannacry/) [verificados]
- Metasploit: `ms17_010_eternalblue` entrega payloads Metasploit padrão (shell reverso/Meterpreter) conforme configuração do usuário; esse detalhe (payloads suportados) não consta na página do Rapid7 DB que li; é prática comum em writeups: ver [HTB Blue writeups](https://rxffsec.github.io/posts/htb-blue) [snippet].

**Fase 5: pós-exploração, movimentação lateral e worm**
- WannaCry: o serviço `mssecsvc2.0` (a partir de `mssecsvc.exe`) lança duas threads, uma varrendo a sub-rede local na TCP 445 e outra gerando IPs aleatórios da Internet para varrer a 445. Kill switch por requisição HTTP a domínio codificado. — [Cisco Talos](https://blog.talosintelligence.com/wannacry/) [verificado]
- A Microsoft descreve propagação como worm para Windows 7/Server 2008 e anteriores sem patch, na rede local e por varredura IPv4 aleatória (ignorando primeiros octetos 127 e ≥224). — [Microsoft](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/) [verificado]
- MITRE ATT&CK lista como software que usa EternalBlue/SMBv1 para movimentação lateral: WannaCry, NotPetya (EternalBlue e EternalRomance), Emotet, TrickBot, InvisiMole, Lucifer, PoshC2 (módulo EternalBlue), além de grupos como Tonto Team, Wizard Spider e Ember Bear. — [ATT&CK T1210](https://attack.mitre.org/techniques/T1210/) [verificado]
- Em labs de CTF, a pós-exploração típica é: shell/Meterpreter com privilégio SYSTEM, `hashdump` e quebra de hashes, busca de flags (THM Blue). — [writeups THM Blue (ex.: Secjuice)](https://www.secjuice.com/write-up-tryhackme-blue) [snippet]

### Inferences
- O ciclo "scan 445 → check de patch → exploit → implante/payload → novo scan 445 a partir do alvo" explica por que o EternalBlue se comporta como worm sem precisar de credenciais; é uma síntese das fontes acima, não uma afirmação de nenhuma delas isoladamente.
- Como o scanner Metasploit e o NSE exploram o mesmo sinal (status de recursos insuficientes em IPC$/FID 0), ambos são "não destrutivos" na prática, mas ainda geram tráfego SMBv1 incomum que a defesa pode detectar.
- Pelo conflito lsass vs. calc.exe, é plausível que o processo-alvo da injeção seja configurável/escolhido pelo operador ou pelo módulo; as fontes lidas não permitem afirmar isso.

### Gaps
- Não consegui ler as páginas da F-Secure (redirecionamento) nem o post original da Countercept (ex.: "kernel DLL injection technique"); as afirmações sobre APC vêm de resumo de busca.
- Não encontrei fonte primária que confirme, para o módulo Metasploit, que a injeção é feita em lsass.exe.
- Não li a documentação do Metasploit em docs.metasploit.com (a URL tentada retornou 404); usei as páginas do Rapid7 DB. Nenhuma página do Rapid7 lida listava "check" do módulo EternalBlue ou os payloads aceitos.
- Valores numéricos exatos dos opcodes/status (0x23/0xc8/0x77; 0x10/0x20/0x30) só foram confirmados via snippet; recomendo verificar no zerosum0x0 ou no código do script Countercept antes de citar em trabalho.
- O RiskSense white paper (Sean Dillon), "EternalBlue RiskSense Analysis 1.2" ([PDF no Packet Storm](https://dl.packetstormsecurity.net/papers/attack/EternalBlue_RiskSense_Analysis-1.2.pdf)), aparece nos resultados e é referenciado pelo módulo Metasploit, mas não foi lido.

## 2. Ferramentas, frameworks e laboratório típico de curso

### Takeaway
O arsenal vazado do Equation Group (FuzzBunch como framework de exploração, DanderSpritz/PeddleCheap como C2/implante, DoublePulsar como backdoor) foi portado para Metasploit (`exploit/windows/smb/ms17_010_eternalblue` e `ms17_010_psexec`) e para scripts Python públicos (worawit). Em cursos, o lab padrão é uma VM Windows 7 SP1 x64 sem patch + Kali em rede host-only isolada, ou as salas "Blue" do TryHackMe/Hack The Box.

### Cited Findings

**Ferramentas**
- O módulo Metasploit é descrito como "a Metasploit port of the Equation Group ETERNALBLUE exploit, released by Shadow Brokers as part of the FuzzBunch toolkit"; créditos: Equation Group, Shadow Brokers, sleepya, Sean Dillon, Dylan Davis, thelightcosine, wvu, agalway-r7, cdelafuente-r7; ranking "Average"; por padrão tenta login anônimo (ou usa SMBUser/SMBPass/SMBDomain se fornecidos); referências incluem o repositório RiskSense-Ops/MS17-010 e o white paper da RiskSense. — [Rapid7 DB – ms17_010_eternalblue](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/) [verificado]
- `ms17_010_psexec`: autores sleepya, zerosum0x0, Shadow Brokers, Equation Group; usa exploits da família EternalRomance/Champion/Synergy; exige named pipe. — [Rapid7 DB – ms17_010_psexec](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_psexec/) [verificado]
- Scanner `auxiliary/scanner/smb/smb_ms17_010`: autores Sean Dillon e Luke Jennings; verifica falta do patch e DoublePulsar. — [Rapid7 DB – smb_ms17_010](https://www.rapid7.com/db/modules/auxiliary/scanner/smb/smb_ms17_010/) [verificado]
- Portes públicos em Python de worawit (repositório "worawit/MS17-010"): existência confirmada apenas por listagem de índice [snippet: [awesome.ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fworawit%2FMS17-010)]; não li o repositório (e não reproduzo código). Autoria "sleepya" nos módulos Metasploit é o mesmo pesquisador por trás dos exploits públicos em Python segundo os créditos do Rapid7 DB [inferência do nome; confirmar].
- Evasões e funcionalidades do DanderSpritz/PeddleCheap descritas pela Forcepoint (ver seção 1). — [Forcepoint](https://www.forcepoint.com/blog/x-labs/evasions-used-shadow-brokers-tools-danderspritz-and-doublepulsar-part-2-2) [verificado]
- O ATT&CK também lista PoshC2 com módulo para explorar SMB via EternalBlue. — [ATT&CK S0378 via T1210](https://attack.mitre.org/techniques/T1210/) [verificado]

**Laboratório típico (conceitual, sem comandos operacionais)**
- Hack The Box "Blue": máquina Windows "Easy" aposentada, lançada em julho/2017; alvo Windows 7 Professional SP1; fluxo comum: varredura Nmap e checagem de vulnerabilidade (NSE ms17-010), depois o módulo Metasploit `ms17_010_eternalblue`, resultando em sessão Meterpreter com privilégio SYSTEM. Um writeup alerta que exploits de kernel podem derrubar o alvo (BSOD) e usou antes o auxiliar `ms17_010_command`. — [snippet de busca; writeups: [rxffsec](https://rxffsec.github.io/posts/htb-blue), [dos-m0nk3y](https://dos-m0nk3y.github.io/hackthebox/Blue), [b4bygroot](https://b4bygroot.github.io/2020/12/09/HTB_Blue_Writeup)] [secundário/snippet]
- TryHackMe "Blue": sala de dificuldade Easy (lançada em 14/09/2020 segundo um writeup), com tarefas: Recon, Gain Access, Escalate, Cracking, Find Flags; usa Metasploit `ms17_010_eternalblue`, `hashdump` e quebra de hashes. Writeups divergem na divisão das tarefas; consultar a sala oficial. — [Secjuice](https://www.secjuice.com/write-up-tryhackme-blue); [jalblas](https://www.jalblas.com/?p=8826) [snippet/secundário]
- Resultados observáveis em lab (do ponto de vista da vítima/defesa): o scan reporta "VULNERABLE" com CVE-2017-0143, risk HIGH (Nmap); o exploit é por vezes instável (várias tentativas, risco de BSOD); sessões e processos novos aparecem no host (ver seção 3). — [Nmap NSE](https://nmap.org/nsedoc/scripts/smb-vuln-ms17-010.html); [Rapid7 DB](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/) [verificados]
- O padrão "VM Windows 7 SP1 x64 sem patch + Kali em host-only" não foi encontrado numa fonte primária única; é consistente com HTB/THM (alvo Win7 SP1) e com o requisito de arquitetura x64 do módulo (ver seção 1), mas a topologia de rede é convenção de curso.

**Aviso ético e legal para o laboratório (texto sugerido para o trabalho)**
- Execute apenas em VMs próprias, snapshotadas, em rede host-only/interna sem rota para a Internet nem para a rede da universidade; um alvo vulnerável a worm não pode ficar exposto à rede, pois SMBv1 sem patch é exatamente o que o WannaCry varria ([Talos](https://blog.talosintelligence.com/wannacry/)). Nunca teste contra sistemas sem autorização por escrito; apague as VMs ao final. As salas HTB/THM são ambientes autorizados. [Recomendação de boas práticas; não é citação de fonte.]

### Inferences
- A diferença Win7 x64 (alvo do módulo EternalBlue) versus alvos x86 ou Server 2008 para `ms17_010_psexec` explica por que, em aula, o módulo psexec costuma ser alternativa quando o EternalBlue falha; as fontes lidas não afirmam isso diretamente além de "mais confiável, mas exige named pipe".

### Gaps
- Não li o repositório worawit/MS17-010 nem o código do FuzzBunch; o nome dos utilitários FuzzBunch (Eternalblue, Doublepulsar, Eternalromance etc.) vem de conhecimento geral e dos textos Forcepoint/Metasploit, sem fonte primária específica lida.
- Não verifiquei as páginas oficiais da HTB/TryHackMe (só writeups); data de lançamento da HTB Blue em julho/2017 vem de snippet.
- Não encontrei guia de lab com topologia "Win7 SP1 x64 + Kali host-only" em fonte citável.

## 3. Detecção: Snort/Suricata, Zeek, Wireshark, logs Windows, EDR/AV e IOCs

### Takeaway
A detecção em rede se apoia em (i) assinaturas Snort/Suricata para a sequência SMBv1 do exploit e para o ping/resposta do DoublePulsar (SESSION_SETUP e Multiplex ID), (ii) anomalias de protocolo no Zeek (pacote EternalSafety), e (iii) varredura ativa com Nmap/Metasploit/Countercept. No host, o evento 3000 do SMBServer/Audit identifica clientes SMBv1, e eventos de criação de processo/serviço (4688, 4697/7045) mostram pós-exploração. Várias das especificidades pedidas (SIDs ET atuais, event ID 3021, nomes Defender "Exploit:Win32/EternalBlue" e "Backdoor:Win32/DoublePulsar") não foram confirmadas.

### Cited Findings

**IDS/IPS (Snort/Suricata)**
- Regra Snort/Talos SID 41978, "OS-WINDOWS Microsoft Windows SMB remote code execution attempt": detecta tentativas de exploração do SMBv1 conhecidas como ETERNALBLUE; categoria OS-WINDOWS; sem falsos positivos conhecidos; referências a MS17-010, Talos WannaCry e SANS ISC; a página mapeia (curiosamente) para ATT&CK T1189 (Drive-by Compromise), mapeamento questionável. — [Snort rule docs 1-41978](https://www.snort.org/rule_docs/1-41978) [verificado]
- A Talos lista cobertura Snort para WannaCry nos SIDs 42329–42332, 42340 e 41978, sem mapear cada SID a MS17-010/ETERNALBLUE/DOUBLEPULSAR. — [Cisco Talos](https://blog.talosintelligence.com/wannacry/) [verificado]; o SANS ISC também recomenda "Check for SID 41978". — [SANS ISC 22304](https://isc.sans.edu/diary/22304) [verificado]
- Emerging Threats (ET): SID 2024430, "ET CURRENT_EVENTS Possible ETERNALBLUE Exploit M3 MS17-010" (rev. 2 em jun/2017), classtype trojan-activity, casa tráfego SMB de qualquer origem para $HOME_NET com conteúdos do cabeçalho SMB e limiar de 10 ocorrências por origem em 1 segundo. — [lista OISF-users, jun/2017](https://lists.openinfosecfoundation.org/oisf-users/2017-June/015138.html) [verificado, mas é um snapshot de 2017; nome e revisão podem ter mudado]

- Countercept inclui 3 regras Snort no repositório do script, voltadas ao comando Trans2 SESSION_SETUP (ping SMB) e respostas distintas; o README diz que assinaturas são fáceis de contornar mas estas são específicas o bastante para detectar reuso dos exploits/implantes sem modificação. — [Countercept/WithSecure README](https://github.com/countercept/doublepulsar-detection-script) [verificado]
- Regra PT Security "NF - EXPLOIT [PTsecurity] DoublePulsar Backdoor installation communication" (ID 5013402), tráfego SMB2/445: não é ET. — [Radiflow ISID](https://isid-analyst.radiflow.com/?p=1501) [snippet]. Regra Snort 5000072 que sinaliza SMB MultiplexID 82 em resposta do servidor como instalação bem-sucedida: [Hackers-Arise](https://www.hackers-arise.com/amp/2018/11/30/network-forensics-part-2-packet-level-analysis-of-the-eternalblue-exploit) [snippet/secundário]. Um post de blog também descreve construir regras Suricata em torno de MID=81 ([HackerNoon](https://hackernoon.com/eternalpulsar-a-practical-example-of-a-made-up-name-629737170a9e) [secundário/snippet]).
- ExtraHop mapeia a detecção "EternalBlue exploit" a ATT&CK T1210 e descreve o ataque como série de mensagens SMBv1 construídas que provocam estouro de buffer e injeção de payload em kernel. — [ExtraHop](https://www.extrahop.com/resources/detections/eternalblue-exploit) [verificado]

**Zeek**
- Pacote `zeek-EternalSafety` (0xl3x1): em vez de assinaturas do exploit, procura violações de protocolo SMBv1 que os exploits precisam cometer. Notices: EternalBlue (cliente SMBv1 intercala SMB_COM_TRANSACTION2_SECONDARY com transação NT_TRANSACT), EternalSynergy (WRITE_ANDX intercalado com outra transação), EternalChampion (assinatura para NT_TRANSACT_RENAME seguido de NT_TRANSACT_SECONDARY), DoublePulsar (servidor muda o campo MID para a faixa 81–83 no meio da transação), ViolationPidMid, ViolationCmd, ViolationTx2Cmd (subcomando Trans2 não implementado), ViolationNtRename. Limitações: suporte SMBv1 do Zeek é limitado; notices baseados em assinatura podem não disparar de forma confiável; alguns são supersets e geram falsos positivos; pacote estável mas sem desenvolvimento ativo. — [zeek-EternalSafety](https://github.com/0xl3x1/zeek-EternalSafety) [verificado]

**Wireshark**
- Campos de display filter existentes e confirmados: `smb.cmd` (inteiro 8 bits, comando SMB), `smb.mid` (16 bits, Multiplex ID), `smb.trans2.cmd` (16 bits, subcomando Trans2). — [Wireshark SMB display filter reference](https://www.wireshark.org/docs/dfref/s/smb.html) [verificado]
- O valor 0x32 para `smb.cmd` (SMB_COM_TRANSACTION2) vem do conhecimento geral do protocolo SMB1 e não foi confirmado por fonte lida; sugerir ao grupo conferir em MS-CIFS. Filtros úteis (a validar em lab): `smb.cmd == 0x32 && smb.trans2.cmd == 0x000e` (ping DoublePulsar, SESSION_SETUP em Trans2) e comparação de `smb.mid` entre requisição e resposta. [Inferência derivada dos campos e do SANS ISC 22312; não é filtro publicado em fonte]
- O zerosum0x0 observa que o Wireshark não tem dissectors para a codificação personalizada do DoublePulsar. — [zerosum0x0](https://zerosum0x0.blogspot.com/2017/04/doublepulsar-initial-smb-backdoor-ring.html) [verificado]

**Logs do Windows**
- Auditoria de uso de SMB1: `Set-SmbServerConfiguration -AuditSmb1Access $true`; depois, no log `Microsoft-Windows-SMBServer\Audit`, cada tentativa de cliente de usar SMBv1 gera evento com ID 3000. — [Microsoft Learn – Detect, enable, and disable SMBv1, SMBv2, SMBv3](https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3) [verificado; página atualizada em 2026-09-08]
- O mesmo documento informa que SMBv1 não é instalado por padrão em nenhuma edição do Windows 11 nem no Windows Server 2019 e posteriores, e (na seção introdutória) que no Windows 11 24H2 e Windows Server 2025 a assinatura SMB é exigida por padrão. — [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3) [verificado]
- O evento 3000 frequentemente registra só o IP do cliente, não a conta; scanners também o geram; o evento 1001 no log SMBServer-Operational é distinto (conexão SMB1 rejeitada por estar desabilitado). — [snippet de busca; fontes: [Lansweeper community](https://community.lansweeper.com:443/t5/forum/smbv1-from-scan-servers/td-p/67536), [Splunk community](https://community.splunk.com/t5/Splunk-Search/How-to-monitor-smbv1-access-on-a-domain-via-splunk/m-p/657118)] [secundário/snippet]
- Evento 4688 (Security, "A new process has been created", auditoria "Audit Process Creation"): campos incluem nome do novo processo, processo criador, token elevation type; a linha de comando só é registrada se habilitada a política "Include command line in process creation events". — [Microsoft Learn – 4688](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4688) [verificado]
- Evento 4697 (Security, serviço instalado, Windows Server 2016/Win10+): Service Name, Service File Name, tipo, conta; recomenda alertar para serviços fora de %windir% ou Program Files. — [Microsoft Learn – 4697](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4697) [verificado]. O evento 7045 (log System, Service Control Manager) não foi confirmado por fonte lida; o módulo `ms17_010_psexec` usa o payload padrão do psexec (execução via serviço), portanto serviços criados remotamente são o artefato esperado [inferência a partir de [Rapid7 DB – psexec](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_psexec/)].
- ATT&CK sugere correlacionar acesso de entrada a portas 445/135 com crashes de serviço, processos filhos suspeitos e comportamento de movimentação lateral (DET0118, AN0327). — [ATT&CK T1210](https://attack.mitre.org/techniques/T1210/) [verificado]. Para movimentação por admin shares: DET0530/AN1468 (acesso a ADMIN$/C$ seguido de criação de serviço remoto, tarefa agendada ou execução suspeita). — [ATT&CK T1021.002](https://attack.mitre.org/techniques/T1021/002/) [verificado]
- Efeito colateral de instabilidade: tentativas de exploração podem derrubar o host (BSOD/reboot) — logo, reinícios inesperados e bugchecks em servidores SMBv1 são pistas. — [Rapid7 DB](https://www.rapid7.com/db/modules/exploit/windows/smb/ms17_010_eternalblue/); [SANS ISC 22304](https://isc.sans.edu/diary/22304) [verificados]

**Mitigação/prevenção (relevante para a seção de defesa)**
- Aplicar MS17-010; desabilitar SMBv1 (KB2696547 citado pela Microsoft); bloquear 445 na borda; usar Defender ATP/Windows 10 recursos. — [Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/); [CISA TA17-132A](https://www.cisa.gov/news-events/alerts/2017/05/12/indicators-associated-wannacry-ransomware) [verificados]

### Inferences
- A combinação mais robusta para um SOC é: bloqueio/segmentação da 445 + auditoria de SMB1 (evento 3000) para achar hosts legados + IDS com regras ET/Snort e Zeek EternalSafety + varredura periódica com NSE/Countercept para DoublePulsar; a ênfase em "violações de protocolo" do EternalSafety é mais resistente a variações do exploit do que assinaturas de bytes (o próprio autor e o Countercept reconhecem que assinaturas são fáceis de contornar).
- Como a vítima típica (Win7/2008 sem patch) frequentemente tem pouca auditoria, a rede (IDS/NDR) tende a ser a camada de detecção mais confiável; o evento 3000 só existe se a auditoria foi habilitada antes do incidente.
- Os SIDs ET de 2017 provavelmente foram renomeados/reorganizados (o SID 2024430 usava a categoria CURRENT_EVENTS); para o trabalho, citar o SID com a data da fonte.

### Gaps
- Não consegui obter a lista atual de regras ET Open/Pro (o arquivo `emerging-exploit.rules` tem ~1,5 MB e só os primeiros 100 mil caracteres foram lidos, sem ocorrências de ETERNALBLUE/DOUBLEPULSAR). Não confirmei SIDs 2024217/2024220/2025650; também não encontrei regra ET nomeada "DOUBLEPULSAR".
- Evento 3021 do SMBServer: não encontrado em nenhuma fonte; evento 7045 (System): não confirmado por fonte lida.
- Nomes Defender "Exploit:Win32/EternalBlue" e "Backdoor:Win32/DoublePulsar": não confirmados (apenas "Trojan:Win32/DoublePulsar" e "Trojan:Win32/EternalBlue" via Wikipédia); não consegui acessar o Microsoft Security Intelligence encyclopedia.
- Páginas Kaspersky/Securelist, Virus Bulletin (403) e Countercept originais não foram lidas.
- Filtro Wireshark exato e valor 0x32 de smb.cmd não confirmados em fonte lida; os valores MID 0x42/0x43 do enunciado não aparecem nas fontes (ver seção 1).
- Event ID 4688/7045 específicos de EternalBlue: nenhuma fonte descreve eventos de host específicos do exploit em si (ele roda em kernel e não gera 4688); apenas os eventos do payload/pós-exploração.

## 4. Mapeamento MITRE ATT&CK e D3FEND

### Takeaway
O mapeamento sólido e citado nominalmente é T1210 (Exploitation of Remote Services, tática Lateral Movement), que lista EternalBlue/MS17-010 em vários procedimentos e WannaCry/NotPetya. T1190 cobre explicitamente SMB exposto à Internet na descrição, mas não cita EternalBlue; T1068 e T1021.002 não mencionam EternalBlue (T1021.002 trata de uso de credenciais válidas); T1203 não foi verificada.

### Cited Findings
- **T1210 Exploitation of Remote Services** (v1.2, tática Lateral Movement TA0008, sem subtécnicas): adversários exploram vulnerabilidades de serviços remotos após entrar na rede; procedimentos citam EternalBlue/MS17-010 (Ember Bear, Tonto Team, Wizard Spider, TrickBot, Emotet, InvisiMole, Lucifer, PoshC2), NotPetya ("two exploits in SMBv1, EternalBlue and EternalRomance") e WannaCry (S0366, "uses an SMBv1 exploit to spread"). Mitigações: M1048, M1042 (Disable or Remove Feature), M1050 (Exploit Protection), M1030 (Network Segmentation), M1026, M1019, M1051 (Update Software), M1016 (Vulnerability Scanning). Detecção: DET0118 (AN0327 correlaciona acesso inbound a 445/135/3389/WinRM com crashes de serviço, processos filhos suspeitos e movimento lateral). — [ATT&CK T1210](https://attack.mitre.org/techniques/T1210/) [verificado]
- **T1190 Exploit Public-Facing Application** (Initial Access TA0001): descrição inclui "standard services such as SMB or SSH" e qualquer sistema com sockets abertos à Internet; a página não menciona EternalBlue/MS17-010. — [ATT&CK T1190](https://attack.mitre.org/techniques/T1190/) [verificado]
- **T1068 Exploitation for Privilege Escalation** (Privilege Escalation TA0004): cobre explorar falhas do SO/kernel para elevar privilégio (inclusive user→SYSTEM, BYOVD); a página não menciona EternalBlue. — [ATT&CK T1068](https://attack.mitre.org/techniques/T1068/) [verificado]
- **T1021.002 SMB/Windows Admin Shares** (Lateral Movement): foca em uso de contas válidas e shares administrativos (C$, ADMIN$, IPC$); não descreve exploração de vulnerabilidades SMB. — [ATT&CK T1021.002](https://attack.mitre.org/techniques/T1021/002/) [verificado]
- Página do software WannaCry (S0366): 16 técnicas Enterprise e 2 ICS, entre elas T1210, T1543.003 (Windows Service), T1486 (Data Encrypted for Impact), T1570 (Lateral Tool Transfer), T1018, T1489, T1490, T1047; T1021.002, T1190, T1203 e T1068 NÃO constam nessa página. — [ATT&CK S0366](https://attack.mitre.org/software/S0366/) [verificado]
- **D3FEND**: D3-NTSA (Network Traffic Signature Analysis), "Analyzing network traffic and compares it to known signatures", relacionada no D3FEND a "Exploitation of Remote Services" em Lateral Movement (mapeamentos marcados como "inferred, experimental"). — [D3FEND D3-NTSA](https://d3fend.mitre.org/technique/d3f:NetworkTrafficSignatureAnalysis/) [verificado]
- Mitigações de gerenciamento já citadas: segmentação de rede e desabilitar recurso/protocolo (SMBv1) — [ATT&CK T1210](https://attack.mitre.org/techniques/T1210/); Microsoft Learn sobre desabilitar SMBv1 — [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3) [verificados]

### Inferences
- Mapeamento recomendado para o trabalho: T1210 (principal; exploração/worm), T1190 quando o SMB está exposto à Internet (inclui a varredura aleatória do WannaCry), T1543.003 para o serviço mssecsvc2.0, T1486 para o ransomware; T1068 só como observação (o exploit remoto entrega execução em kernel/SYSTEM, mas o ATT&CK não o atribui a EternalBlue); T1021.002 aplica-se ao `ms17_010_psexec`/PsExec e a movimentação posterior com credenciais, não ao exploit em si. Esses mapeamentos são interpretação do relator, não afirmações do MITRE.
- O mapeamento de D3FEND para detecção (NTSA) e para mitigação (patch, desabilitar SMBv1, segmentação) é coerente com as mitigações M1051/M1042/M1030 do ATT&CK, mas outras técnicas D3FEND (ex.: relacionadas a atualização de software e filtragem de tráfego) não foram consultadas.

### Gaps
- T1203 (Exploitation for Client Execution) não foi consultada; provavelmente não se aplica, pois o vetor é um serviço de rede, não execução no cliente.
- IDs D3FEND além de D3-NTSA (ex.: Software Update, Network Isolation, Inbound Traffic Filtering) não foram verificados.
